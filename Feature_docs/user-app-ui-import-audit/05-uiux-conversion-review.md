# 05 — UI/UX & Conversion Review: Friend's Flutter UI (shodasha-friend-ui)

Reviewer: UI/UX + product-conversion audit against our committed goals
Source app: `C:\Users\Hp\AppData\Local\Temp\opencode\shodasha-friend-ui` (Flutter, Firebase-inited, single-device mock state)
Product truth used: `context/project-overview.md`, ADR-107 (COD idempotency UX), ADR-110 (UPI verify/polling, deposit visibility), ADR-111 (empties/deposit handling, POD).

TL;DR: The friend's app is **a beautiful mockup wrapped around a fake machine**. The visual shell (dense retail cards, status pills, strong CTAs, gradient heroes) is genuinely transplantable. But every conversion-critical flow inside it — booking, confirmation, payment, deposit, support, reorder — is either missing, hardcoded, or actively dishonest (fake PINs, fake rider, fake ETAs, fake UPI history, wrong SKU prices of Rs 60–65 vs our committed Rs 28/30). Imported as-is it would lower conversion for the Bhopal repeat-order customer; imported as "look, not logic" it raises it.

## 1. First impression & brand feel

**Actual design language** (from `lib/core/constants/app_constants.dart`, `lib/core/theme/app_theme.dart`, and the screens — note `app_theme.dart` is dead code, `main.dart:24-33` inlines its own `useMaterial3: false` theme, so screens run on hardcoded colors):

- **Palette**: "Eco-Pure" teal `#0D9488` primary + deep teal `#115E59` + solar yellow `#FACC15` accent (`app_constants.dart:5-9`), slate-grey text scale `#0F172A / #64748B`, background `#F8FAFC` (`app_constants.dart:11-18`). BUT screens simultaneously hardcode a **second palette** — green `#16A34A` as action/confirmation color (`login_screen.dart:383`, `cart_checkout_sheet.dart:215`, `order_card.dart:227`, `top_bar.dart:107`). Result: teal and green fight for "primary" between screens; there is no single source of truth.
- **Surface grammar**: white cards, 16px card radius / 10-12px chips (`app_constants.dart:31-35`), hairline `#E2E8F0` borders + very light shadows (`black.withOpacity(0.03)`) — `live_purity_card.dart:23-29`, `order_card.dart:19-33`. It reads as a Flipkart/Blinkit-grade dense retail look, which is the right register for a Bhopal household utility app.
- **Typography**: Roboto, w900 display headers with negative letterSpacing, 10–12px uppercase tracked micro-labels ("FEATURED WATER CANS", "CAN SECURITY LEDGER") — `app_theme.dart:23-48`, `featured_products.dart:107`, `wallet_screen.dart:89`. The type system's own comments say "Flipkart Banner / Section Headings" (`app_theme.dart:22`) — the intent is explicit and on-target.
- **Status language**: amber pill for pending, emerald for delivered/paid, red for paused, blue for ETA — `order_card.dart:50-65`, `rider_dashboard_screen.dart:172-176`. Good, legible semantic color.

**What is genuinely strong (keep-worthy):**
- Dense retail order cards with ID + status pill + qty badge + price (`order_card.dart:38-133`) — closest match to our "firm confirmation" surface.
- Big 48–52px full-width CTAs, consistent `labelLarge` w800 letter-spaced button text (`app_theme.dart:66-70`, `cart_checkout_sheet.dart:210-273`).
- The 4-box OTP input row with focus chaining (`login_screen.dart:473-503`) — clean, modern, phone-field with `+91` prefix (`login_screen.dart:350-374`).
- Segmented portal switcher, rounded 36px-bottom login hero (`login_screen.dart:189-323`).
- Gradient hero cards for wallet/subscription/support (`wallet_screen.dart:30-35`, `support_help_screen.dart:81-86`) — eye-catching but restrained.
- Offline-capable empty states pattern in rider dashboard (`rider_dashboard_screen.dart:134-151`).

**Where it drifts into decoration / fake premium:**
- **Jet-plane marketing copy**: the subscription screen is promotional copy in app clothing — "MILK-RUN SUBSCRIPTION", "SET UP 7:00 AM MILK-RUN SCHEDULE", "Guaranteed 7:00 AM Delivery", "Zero hassle. Doorstep drop before your family wakes up." (`orders/subscription_screen.dart:33,125,156-158`) — a guaranteed 7 AM is a promise the ops model (rider routes, no per-minute tracking) cannot keep. Same disease in the top bar: "Detect Real Device Location (GPS)" / "Querying satellites & reverse geocoding..." / "Live sensor GPS coordinates & postal address worldwide" (`top_bar.dart:252-257`) — developer-bragging copy exposed to customers.
- **English premium-app tone throughout** — see Section 5. One single Hindi string exists in the entire app (`support_help_screen.dart:48`).
- **Decoy UI**: a `const` search bar that is a painted Container, not an input (`top_bar.dart:569-580`); hard-coded cart badge `'2'` (`top_bar.dart:542`); a decorative person-icon button with no handler (`top_bar.dart:518`); subscription "Custom Days" checkboxes with `onChanged: null` (`subscriptions/subscription_screen.dart:45-50`).
- **The "live purity" theater**: a fake telemetry singleton with hardcoded `tdsValue: 85, phValue: 7.2, batch 'BHP-X4-2026'` (`plant_service.dart:8-12`) dresses manual data entry as "LIVE PURITY LAB TELEMETRY" (`plant_hub_screen.dart:231,252-256`). The customer-facing `LivePurityCard` is actually **dead code — never mounted anywhere** (defined `live_purity_card.dart:6`, zero usages). The "live" data isn't live and the visible part isn't even shown; the risk is conceptual, the waste is real.

**Legibility & accessibility defects inside the "premium" look** (worth fixing at import, not keeping):

- Chip/label font sizes run 8.5–10px in the densest cards — `live_purity_card.dart:131-132` (8.5px sublabels), `plant_hub_screen.dart:405` (9px), `order_card.dart:62`/`subscription_service` pills (10px). Adults 40+ in our target cohort cannot comfortably read <10px; when this pattern reaches a *trust* surface (deposit line, PIN, window) it becomes a conversion problem, not a style nit. Floor: 11px (body 12.5–13px, current bodyMedium is 13px — that part is fine).
- `AppConstants.minTapTarget = 48.0` is defined (`app_constants.dart:33`) but barely enforced: qty-stepper `IconButton`s and the address modal's per-row edit/delete icon buttons have visible-size well below 48 (`cart_checkout_sheet.dart:167-188`, `top_bar.dart:306-316`). For refill/empties counters touched with wet hands at the doorstep this matters.
- `const` emoji glyphs as product atoms (`💧` `🧊` `🚚` in `cart_checkout_sheet.dart:60,141`, `order_card.dart:80`) render inconsistently across cheap Android skins common in tier-2/3 markets; replace with the existing Material water-drop icon set before import.
- Beverage-grade contrast is mostly good (slate on white), but the yellow accent `#FACC15` with brown text `#78350F` (`mode_selection_cards.dart:160-183`) and light-on-yellow badge text (`top_bar.dart:542`) sit near the contrast floor — the subscription tile is the least readable surface on the app, and it's the one we want to push.

### 2c. The 30-second reorder test — timed against the friend's flow

Committed goal: an existing customer reorders (same jars, address, window) in under 30 seconds. Running it literally in the friend's app, as a returning household user:

1. **Open app → login gate every launch** (`main.dart:34` always returns `LoginScreen`; no auth persistence anywhere). Re-enter phone + OTP: ~20–35s by itself before any water screen appears. *A returning user never skips the 500-line gate.*
2. **No session, no defaults**: nothing in the app persists an order, cart, qty, address choice, or slot between sessions — `OrderStateNotifier`/`AddressStateService` are in-memory singletons rebuilt fresh per run (`order_service.dart:34-36`, `saved_addresses_screen.dart:26-28`). There is no "last order" to default from.
3. **Choose a path to water**: Home shows two marketing tiles + the product list. If the user lands on the Instant tile → sheet opens qty=1 (`mode_selection_cards.dart:20`) — but the household ordered 2 last time (yesterday's completed order is invisible: `my_orders_screen.dart:25-38` never renders completed orders, so they can't even *see* what they had).
4. **Set a slot? Not here**: slot selection lives only in the top-bar address modal; the instant sheet books with a hardcoded `'Express Delivery (~30 mins)'` promise (`mode_selection_cards.dart:82`).
5. **Confirm**: order is created with the hardcoded Arera Colony address and `'#SHD-8...'` id; user is yanked to My Orders (`:97`) — which shows a card whose ETA (`~25 mins`, `order_service.dart:113`) and rider (`Mahesh`) are fiction, and which displays their "DELIVERY PIN" to them and offers them the rider's deliver button (`order_card.dart:190-248`).

**Total honest reorder time: impossible — the test cannot even complete** because step 1 has no skip and step 2 has no memory. In our design the same run is: open → BOOK NOW (pre-filled 2 jars / Home / morning) → firm confirmation → done, ~10s. The gap between those two walks is the actual conversion risk in importing this design's *flow*, as opposed to its *look*.

### 3b. Deep dive — the five screens that carry conversion

**Login (516 lines) — is the premium treatment worth it for a low-income household?** Partially. The hero + portal switcher + role-detect card is ~200 lines of theatre (`login_screen.dart:188-239,413-450`) that adds vertical scroll before the first input on a 5" screen — every extra screen-height the user walks through before water is friction, and for partners only. But the *atoms* are excellent: 58px OTP boxes with auto-advance (`:473-503`), a `+91` prefix field with 10-digit validation (`:62-66`), floating snackbars, resend countdown. Net judgment: keep every atom, cut the page to one visual beat — brand mark → phone field → OTP. Merge the two portals behind a server-detected role (a rider logging in with their number can silently land in the rider app; households should never see a "Partner / Staff" toggle, `:287-319`).

**Mode selection cards — what "modes" exist vs our Ek Baar / Roz ka Plan.** Friend's taxonomy is **Instant Delivery** (`mode_selection_cards.dart:115-150`) and **Subscription** (`:154-188`). Mapping to ours: "Instant" ≈ Ek Baar — but ours is *window-based one-off ordering*, not a 45-min express service (promise we don't operate, `:144-146`); "Subscription" ≈ Roz ka Plan — ours is pause/resume-first with deposit already paid, not "Daily / Alternate schedule" tiles that launch a calendar screen with no money in it. Critically the friend's "modes" don't share state with anything: the instant sheet can't see the subscription, the subscription can't see neither address nor window, and all three booking paths use three different address sources. In our model Ek Baar and Roz ka Plan are the same order payload with `repeat: true | false` — that's what makes the machine feel like one machine.

**Cart checkout sheet — does the stepper/qty/deposit/empties exchange exist at all?** Qty stepper exists and is well-built (`cart_checkout_sheet.dart:160-191`); the *empties exchange* step does not — the rider field `emptyCansToReturn` is silently set equal to ordered cans (`:229`) with no customer-facing stepper, no "returning empties reduces deposit" feedback loop; the *deposit* step does not — no line item, no ₹150 visibility, which is our committed booking-time disclosure (goal 2 + ADR-111); the *payment* step does not — no UPI/COD chips (ADR-110). Net: the sheet is 1 of 4 required stages, dressed as a finished checkout.

**My Orders + order card — the tracking surface.** This card is 90% of our firm-confirmation visual (`order_card.dart:16-254`) and worth importing nearly as-is once three things change: (i) history rows + reorder CTA (repeat game), (ii) rider's real name + `tel:` call button surfaced from the data that already exists in `order.deliveryAgent` (`order_service.dart:11`), (iii) the arrival-window line ("9:00–9:30 AM pahunching") replaced from fake `~12 mins` (`order_card.dart:208-215`). The PIN box stays only if PIN distribution becomes honest.

**Support & wallet — the aftercare pair.** Support has the right *questions* and no real *answers* (`support_help_screen.dart:153-176` is a fine complaint taxonomy; every button is a fake dialog, `:44-50,110-137`); wallet has the right *deposit sentence* (`wallet_screen.dart:94-96`) and no real *money* (`:55,105-122` all hardcoded). During import, support becomes the tab + wa.me; wallet's ledger card migrates into profile and checkout; both surfaces stop inventing numbers and start showing ledger truth.

## 4. IA & navigation

**Tabs: friend has 5 — Home / My Orders / Subscriptions / Wallet / Profile** (`customer_home_screen.dart:81-107`). Our committed IA is **4 tabs: Home / Orders / Support / Profile**. Consequences:

- **Support is missing as a destination.** The single support screen is unrouted; customers only reach snackbar stubs in Profile. Our WhatsApp-first commitment (project-overview.md:12) needs a *tab*, not a buried tile — that's where complaint volume converts to WhatsApp sessions.
- **Wallet as a top-level tab is over-promoting a passive surface.** In our product the wallet is mostly the deposit/refund ledger (ADR-110 security-deposit visibility). ₹28 refills don't justify prepaying wallets; wallet belongs in Profile, freeing a tab for Support.
- **Subscriptions as first-class tab is right** — resume it; it matches the standing-order business and pause/resume self-service metric.
- **Notifications live only behind the top-bar bell** (`top_bar.dart:509-514`), not in tabs or profile — fine, but the screen is fake data.
- **Dead ends / orphans (a full inventory!)**: `SupportHelpScreen`, `SavedAddressesScreen`, `orders/subscription_screen.dart` (duplicate), `LivePurityCard`, `AppBottomNavBar` (`customer_home_screen.dart:71-108` builds its own inline `BottomNavigationBar` instead), `AppTheme` (`main.dart:24-33` inlines its own), `HomeDataProvider`, the `completedOrders` list, and the shared models package (`shared/models/product.dart` — unused). Roughly one-third of the codebase is decoration the user can never reach.
- **Ordering crosswire**: customer order card launches the rider delivery flow (`order_card.dart:232-247`); customer profile launches the owner console (`customer_profile_screen.dart:106-109`). Roles are blended because there's only one in-memory state class (`OrderStateNotifier.instance`) shared by all three "surfaces" — fine for a prototype, fatal as an architecture import (our surfaces are separate user app / vendor app / super-admin).
- **Address state is split-brained**: `TopBar._savedAddresses` (strings, GPS-augmented, `top_bar.dart:22-102`) vs `AddressStateService` (models used by checkout, `saved_addresses_screen.dart:26-88`) vs hardcoded literals inside booking sheets. Checkout may show one address while the top bar advertises another.

**Notification surface — the WhatsApp bridge.** The friend's notification list exists only as fake rows (`notifications_screen.dart:9-42`), reached from a bell in the top bar. In our product this surface earns a real job: every real notification (order confirmed, rider assigned, deposit refund processed) is both an app push *and* a WhatsApp-worthy share point — ADR-110's confirmation copy ("Order ID, time, amount") and ADR-111's refund events are exactly what a Bhopal household wants to forward to the family group. Import decision: keep the bell + list UI shell, bind each row to a real event, and give non-negative rows a one-tap **"WhatsApp par share karein"** action instead of the friend's dead `unread` dots. Notifications must never carry information the ledger doesn't confirm — the fake "Rs 500 Deposit Recharged" row (`:34-41`) is the pattern to forbid.

**Proposed tab migration (friend's 5 → our 4):**

| Friend's tab | Our destination | Migration |
|---|---|---|
| Home (`customer_home_screen.dart:56`) | **Home** — keep tab, replace content | Top bar shrinks to a slim location strip; `ModeSelectionCards` becomes the Ek Baar / Roz ka Plan hero machine with BOOK NOW; `FeaturedProducts` survives as a secondary sheet (SKUs corrected to Rs 28 / Rs 30 + deposit FAQ) |
| My Orders (`:57`) | **Orders** — keep tab, add history + reorder | Active cards keep the `order_card.dart` grammar; add completed list (data exists in `order_service.dart:55-70`), per-order bill-share to WhatsApp, and the "Phir se yahi order karein" CTA |
| Subscriptions (`:58`) | Fold into **Profile** as a subscription section, or keep as a visible card inside the Roz ka Plan flow on Home | Avoid duplicate subscription IAs: only one plan surface (`orders/` twin dies); monthly total + activation button (ADR-100) required to keep the tab |
| Wallet (`:59`) | Fold into **Profile** as the deposit/refund ledger card | Keep the `wallet_screen.dart:76-99` ledger card verbatim; balance card becomes a statement view from the real ledger — it stops being a tab |
| Profile (`:60`) | **Profile** — keep | Remove Owner Control Center and fake identity; add Name/Phone/Gmail editing (ADR-110), addresses, deposit ledger, logout |
| *nothing* | **Support — new tab** (our 4th) | Build from `support_help_screen.dart` (it survives as the only real support UI ever written in this app): wa.me deep link with order context, share-bill, call button, issue list |

## 5. Bilingual & tone fit — will Bhopal households convert?

**No — not on this copy.** Tier-2/3 household decision-makers (the person handing ₹30 and empties at the door) read Hindi/Hinglish comfortably and English commands poorly; the app's English is also *stylized* ("VERIFIED ROLE IDENTIFIED", "CONFIRM INSTANT DISPATCH", "MILK-RUN", "Operational Gateway") — the register of a fintech pitch deck, not a waterwalli app. The one Hindi string that exists is buried in an unrouted screen (`support_help_screen.dart:48`). Trust copy (deposit, refund, arrival window) must be understood infrastructurally — in the customer's first language first.

**Import strategy: keep the look, swap the copy culture.** Preserve the dense-retail visual system (skeleton, pills, CTAs). Reset all strings to **Hinglish-first** (Roman-script Hindi, the Bhopal default reading register) with a Hindi variant later. Translate *teaching* copy (explainers, deposit notes, status lines) fully to Hindi; keep short action verbs Hinglish.

Five real strings to rewrite (actual code, actual replacement):

| File:line | Friend's string (as coded) | Import rewrite (Hinglish-first) |
|---|---|---|
| `login_screen.dart:232` | `'Pure 20L mineral water delivered directly to your doorstep in Bhopal'` | `'Shuddh 20 litre ka paani — roz, turant, aapke darwaze tak'` |
| `login_screen.dart:390` | `'Get Verification Code'` | `'OTP bhejein'` |
| `mode_selection_cards.dart:99` | `'CONFIRM INSTANT DISPATCH'` | `'Ye paani booked karein'` (with the deposit line above the button) |
| `cart_checkout_sheet.dart:255` | `'Order Confirmed! Van is on the way 🚚'` | `'Order pakka! Order #SHD-4821 • Rider 5:00–5:30 PM ke beech aayega'` (firm ID + window, not a van vibe) |
| `orders/subscription_screen.dart:156-158` | `'Guaranteed 7:00 AM Delivery' / 'Zero hassle. Doorstep drop before your family wakes up.'` | `'Roz subah paani — aapki chuni hui window mein'` + refundable-deposit note (make the honest version of the promise) |

Also watch: currency formatting flips between `Rs 65.00` (`cart_checkout_sheet.dart:204`) and `₹450.00` (`wallet_screen.dart:55`) — pick one (₹). And `support_help_screen.dart:181` claims "ISO 9001:2015 Certified" in dead code — only ship certification badges that are true.

**Copy register by surface type** (the rule of thumb for the import's string pass):

| Surface | Register | Rule |
|---|---|---|
| Actions (buttons, chips) | Short Hinglish | "Book karein", "OTP bhejein", "Cod chunein" — verbs stay Roman-Hindi, no English premium verbs ("DISPATCH", "HANDSHAKE", "MILK-RUN") |
| Money & deposit lines | Full Hindi/Hinglish, straddling no jargon | "Rs 150 per can jaman ke liye — wapas mil jayega" (deposit is the sentence a user must never have to translate) |
| Status & windows | Hindi + numbers | "Rider 9:00–9:30 ke beech pahunchega" — the window itself is bilingual-agnostic but the name/time format must match Indian SMS conventions (not "ETA ~20 mins") |
| Trust/quality claims | Measured Hindi, dated | "9 Oct report: TDS 85 ppm (safe limit se neeche)" — claims cite date + number, never "LIVE", "100%", "Guaranteed" |
| Empty/error states | Warm Hinglish + one real action | "Pani khatam ho gaya? Agla delivery subah 8–10 baje — yahi order dobara karein" |

One more tonal detail from the friend's code worth keeping: the app never talks down to the user — it uses exactly no condescension (no "Dono behtar" hedges, no double-language confusion inside one screen). That consistency is a virtue of the design's copy *system* even though its language is wrong; the import should keep that single-register discipline and only change the register to Hinglish.

## 6. Trust & ethics flags (cut or make honest before launch)

These are the things that would *actively lie* to a user if the design were wired to anything:

1. **Delivery-PIN theater** — PIN shown to the rider as a hint (`rider_delivery_screen.dart:141`), wrong-PIN error *prints the correct PIN* (`rider_delivery_screen.dart:30`), and the PIN is already visible on the customer's card (`order_card.dart:190-206`). OTP-based delivery verification that verifies nothing. Cut or make honest: PIN shared only via WhatsApp/order sheet, never echoed to the PIN-holder.
2. **Customer-performs-rider-action leak** — "RIDER: ENTER PIN & DELIVER CANS" on the customer card (`order_card.dart:222-248`) lets the "customer" complete their own delivery locally. Role boundaries must exist per surface (three surfaces, per project-overview.md:5).
3. **Fabricated purity & compliance claims** — "LIVE PURITY LAB TELEMETRY" with manually typed TDS/pH (`plant_hub_screen.dart:40-110`, `plant_service.dart:8-12`), fake notification "Today's batch TDS tested at 110 ppm. 100% compliant with BIS" (`notifications_screen.dart:27-29`), "ISO 9001 & BIS IS 14543 Certified" tile (`customer_profile_screen.dart:131-133`). For a *consumable*, fake lab data is the worst lie on this list. Replace with a daily batch lab card shown as a **real, dated achievement** ("Aaj ki batch test: TDS 85 ppm • 9-Oct report 📄"), never "live".
4. **Guarantee-fictions** — "Guaranteed 7:00 AM Delivery", "Get water within 45 mins", "Set Exact Specific Delivery Time", fake static ETAs `~12/~20/~25 mins`. All replaced by the one honest mechanism: a firm 30-min arrival window on a firm confirmation.
5. **Fabricated money-life** — fake wallet balance/passbook/UPI recharge history (`wallet_screen.dart:55,105-122`), fake "Deposit Recharged Rs 500" notification (`notifications_screen.dart:34-41`), fake "Ticket Raised… 15 minute ke andar contact karegi" (`support_help_screen.dart:44-50`), fake day-end cash audit (`plant_hub_screen.dart:364-370`). Under ADR-110/111 every rupee surface must bind to the ledger.
6. **Identity/role fakes** — hardcoded rider/vendor phone whitelist shipped client-side (`login_screen.dart:30-34`); any 4-digit OTP accepted (`login_screen.dart:90-124`); partner roles detected client-side; "Owner Control Center" exposed to customers (`customer_profile_screen.dart:99-111`) showing other customers' data (mock today, pattern still wrong).
7. **Decorative interactive elements** — fake search (`top_bar.dart:569-580`), hardcoded cart badge "2" (`top_bar.dart:542`), dead avatar button (`top_bar.dart:518`), disabled Custom-Days checkboxes (`subscriptions/subscription_screen.dart:45-50`), published "Recharge Gateway will open shortly" (`wallet_screen.dart:60`).

## Verdict

**As built, the friend's design lowers our conversion for exactly the customer we serve** — the Bhopal household that reorders when the water runs low. The machine at the heart of this product is absent (no BOOK NOW, no persisted defaults, no reorder path, no history), the money conversation is hidden (no deposit at booking, no payment step, fake wallet), and the trust surfaces deliberately lie (guaranteed 7 AM, "~20 mins", live purity, PIN hints). A tier-2/3 household would also find the English premium register foreign — a single Hindi sentence exists in the whole codebase, inside an unreachable screen. What the design *does* raise is **perceived polish**: the dense-retail card system, status pills, OTP atoms, and gradient heroes are real, transplantable craft — better visual bones than we'd have sketched from scratch.

**Import posture: take the shell, reject the machine, rebuild the machine inside the shell.**

The 3 highest-leverage UX changes during import:

1. **Make the home screen the repeat-order machine.** Replace top-bar chrome + mode tiles + product list with one hero card: last quantity, last address, last window pre-selected, big BOOK NOW, ₹150/jar refundable-deposit line shown whenever new jars are bought, 30-min window chip visible. One tap → firm confirmation screen (order ID + window + amount). This single change addresses goals 1(a)(c)(b) and the <30s reorder metric.
2. **Finish the checkout honestly.** Keep the friend's checkout sheet geometry; add the missing three rows — empty-jar exchange stepper with refundable-deposit math (ADR-111), UPI/COD chips (ADR-110 with honest poll + "Retry karein"/"COD chunein"), firm-confirm state replacing the fake "DISPATCHED + Mahesh + ~20 mins" jump. Additionally: single address service as truth of record; kill the millisecond order IDs.
3. **Wire language + WhatsApp into the frame.** Ship Hinglish-first copy for every shell string (Section 5 table is the starter set), and make Support a 4-tab citizen with real `wa.me` deep links carrying order ID/context — converting the friend's good issue taxonomy into actual resolution sessions.

In one line: the friend built the showroom; the import is about installing our engine inside it — and cutting everything that pretends the engine already runs.

**Acceptance bar for the import's UX reviewer** — the design only ships if all of these read true against the rebuilt app:

- Opening the app on a second device (or after clear-data) still shows login → then defaults; deleting app data loses *nothing* the user has already booked or saved from the ledger.
- Every rupee on screen traces to an API response (quote, ledger, order) — no `withOpacity`-styled fiction.
- A fresh Bhopal household user can complete a first order in the guest path by reading only Hinglish copy; every promise in view is one the ops dashboard can actually see (window, rider, deposit count).
- `wa.me` opens on every support tap; the order card carries no rider actions; the purity surface shows a dated report, never a pulse.
